# Trip.com migration: attribution validation (read this first)

Prepared 2026-10-21 on branch `tripcom-on-redesign` (from production `main` at `a882153`, i.e. after the 2.0 redesign and the homepage slider).
**Nothing here is deployed.** Production still serves the Booking.com (CJ) links.

The goal is verified tracking and commission attribution, not replacing buttons. Every statement below is marked as
**Official** (read on trip.com/partners on 2026-10-21), **Tested** (our own checks), **Unproven**, or **Ask Trip.com**.

## 1. What the official Trip.com documentation establishes

Sources: `/partners/help/faq/tools`, `/faq/report`, `/faq/commission`, `/faq/integration`, `/faq/account`, `/partners/index`.

| Topic | What it says | Consequence for us |

| Links must come from the generator | "You must use the links generated by the Trip.com Affiliate Platform in order to receive commission... you must not modify affiliate links." They run "a set of parameter verification processes". | Registry stores the generator's exact string with a SHA-256; the validator rejects any href that differs by one character. No link is built, shortened or re-encoded by us. |

## 2. What our own technical tests establish

All run locally; no Trip.com, CJ or analytics traffic is generated, and no affiliate URL is ever requested.

| Test | Result |
|---|---|
| Registry rebuilt against the redesigned pages | 142 destinations; 1,567 booking links on 202 served pages today; 1,503 need a Trip.com link; 64 removed by earlier owner decisions; 0 blocked by open decisions. |
| Worksheet | 106 unique Trip.com destinations (97 hotels, 9 city lists) cover all 1,503 links. |
| Full-site conversion preview (plain trip.com URLs, no tracking, in a temp directory) | 202 pages convert, 1,503 Trip.com URLs, 64 buttons removed, 261 disclosure rewrites, 0 unknown disclosures, 0 validation failures. |
| Pipeline self-test (`selftest.js`, synthetic fixtures in a temp copy) | 19/19: accepts well-formed hash-locked links; rejects edited parameters, wrong Alliance ID, wrong SID, wrong property, CJ/Booking leftovers, missing destination, shorteners/redirects, unregistered Trip.com URLs, missing disclosure, missing rel, a link changed after import, unconfirmed links, a missing/unapproved format profile, an unapproved regional host. |
| Pilot dry run on the real registry | Blocked as intended: no official links exist yet. |

These tests prove the **mechanics** (right link on the right button, nothing modified, nothing left over, disclosure present, reversible). They prove **nothing** about Trip.com crediting a booking.
A GA4 `affiliate_click` event is only a click on our own page. It is never treated as attribution anywhere in the tooling.

## 3. What remains unproven without a genuine booking

1. That a link generated for account 11013066 / site 333523744 is credited when a real customer books from our site.
2. That date-neutral hotel links and city lists are credited the same as a dated deep link.
3. That the domain the generator produces (www.trip.com vs a regional domain) is the one the Vietnam programme expects.
4. That a booking made on mobile web or in the Trip.com app after clicking a link on our site is credited (cookie 30 days web / 7 days app).
5. The commission rate and any account-specific restrictions (read from your Commission Plan).
6. That a first-party reverse proxy or our own redirect would be acceptable: not used, not needed.

A technically working link does not guarantee tracking. Only the Booking report (T+1) and later the Commission report can show it.

## 5. Dated links, domain conflict, link format: how the tooling treats them

- **Dated links:** a generated URL containing check-in/check-out parameters is rejected on import (`fixed date parameter`). If the generator ever produces one, set `accept_dated` in the profile only after Trip.com explains behaviour after the dates pass. The URL is then preserved exactly.
- **Domain:** `link-profile.js derive` records the host the generator actually produced. If it is not `www.trip.com`, the profile cannot be approved until `domain_decision` is written (with the support reply).
- **Format:** unknown until your first links exist. `apply.js` refuses to run without an approved profile; after approval every link must match its host, path shape and parameter set exactly.

## 7. Minimum evidence before the full cutover

Proposed gates (also tracked by `node scripts/tripcom/readiness.js`):

1. Account facts attested (checklist) and written answers from Trip.com on domain, date-neutral links and attribution window.
2. All 106 links generated by the dashboard, imported, hash-locked, each opened by you and confirmed to show the right property; format profile approved.
3. Technical: `apply.js` dry run 0 blockers; `validate.js --cutover` 0 failures on the converted tree; self-test green.
4. **Pilot:** at least one genuine customer booking from a pilot-page link visible in the Booking report with the expected hotel and booking date (this is the first real evidence of attribution), and ideally the matching eligible line in the Commission report after the stay.

**Reality check on traffic.** Search Console (last 3 months) shows 623 clicks across the whole site, and 0-3 clicks per quarter on each pilot hotel page. At that volume a pilot may see no booking for months, so gate 4 may not be reachable quickly on any small set of pages. The honest options are (a) wait, (b) widen the pilot to higher-traffic pages (see `PILOT-PLAN.md`), (c) ask Trip.com for click-level confirmation (question 3), or (d) you accept, in writing, a cutover on gates 1-3 plus click-level confirmation, with the Booking report watched from day one and CJ kept active so rollback stays instant. That is a business-risk decision for you, not something the tests can settle. Self-referrals and artificial bookings are not an acceptable shortcut and are not built into any script.

## 8. Reconciling GA4 with Trip.com reporting

- GA4: `affiliate_click` (provider `tripcom`, `hotel_name`, `page_path`, `cta_location`, `link_key`) counts outbound clicks per page and placement.
- Trip.com: the Booking report lists orders (T+1). Compare by date: a booking at time T should be preceded by a GA4 click from the same day or within 30 days. Per-page attribution inside Trip.com is not available unless a sub-ID exists (question 6).
- Expect far fewer bookings than clicks; the ratio is unknown until data exists. Do not read a low or high click-to-booking ratio as proof of anything until Trip.com confirms click-level tracking.
